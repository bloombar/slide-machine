# Internationalization (i18n)

[TECH-12](SPEC.md#tech-12-internationalization-i18n--localization) — the
application UI localized into English, French, Spanish, Russian and Mandarin.
This page is the design and the record of what shipped: the library choice, the
locale-resolution order, and the UI/content scope boundary.

Tracked as [issue #128](https://github.com/bloombar/slide-machine/issues/128).

## Scope

**In:** the application UI/chrome — menus, buttons, labels, placeholders,
`aria-label`s, toasts, error messages, and date/number formatting.

**Out:**

- **The admin console.** Per the owner's call on #128, `/app/admin/*` stays
  English-only: [`pages/Admin*.tsx`](../client/src/pages/), [`components/admin/`](../client/src/components/admin/),
  [`AdminShell`](../client/src/components/layout/AdminShell.tsx), [`RequireAdmin`](../client/src/auth/RequireAdmin.tsx),
  [`api/admin.ts`](../client/src/api/admin.ts), and [`lib/date.ts`](../client/src/lib/date.ts)
  (used only by admin pages). The way in is English too: the hamburger's
  **Admin** entry in [`ShellMenu`](../client/src/components/layout/ShellMenu.tsx)
  is a hardcoded `ADMIN_LABEL`, not a translation key.
- **Slide and quiz content.** Translating a deck's content is a separate,
  on-demand post-lecture feature — [SHARE-2](SPEC.md#share-2-post-lecture-translated-viewing),
  currently a type-only stub (`SlideTranslation` in [deck.ts](../shared/src/types/deck.ts)).
  Live translated generation stays out of scope ([§2.2](SPEC.md#22-non-goals)).

### Two different "languages" — keep them apart

The `User` type carries **two** locale fields and they are deliberately
independent:

- **`User.locale`** (required, defaults `en`) — the **interface** language.
  This is what TECH-12 is about.
- **`User.language`** (optional) — the **lecturing/generation** language: what
  speech recognition listens for and what the AI writes slides in, with an
  inherit cascade (lecture → project → profile → browser) and its own picker,
  [`LanguageSelect`](../client/src/components/LanguageSelect.tsx).

An instructor can run the UI in English and lecture in French. Per SPEC the
lecturing language now *defaults to* the interface locale: the profile's
inherit option reads "your interface language".

## Library: react-i18next + `i18next-icu`

SPEC suggests "react-i18next / FormatJS with ICU message format". We picked
**react-i18next**, and the deciding factor was the test suite.

There are ~80 client test files, each with its own local `renderX()` helper,
and many assert literal English accessible names. `useTranslation()` reads a
**module-level singleton**, so initializing i18next once in
[`test/setup.ts`](../client/src/test/setup.ts) with the eager `en` bundle keeps
every one of those tests passing untouched. FormatJS's `react-intl` requires an
`IntlProvider` ancestor in every render tree, i.e. ~80 helper edits before a
line of feature code. After extraction, a test that fails signals a *wording*
change — exactly the signal we want, and one a wall of provider plumbing would
have buried.

ICU message format, which SPEC requires, comes from the `i18next-icu`
post-processor.

Packages in the `client` workspace: `i18next`, `react-i18next`, `i18next-icu`,
`intl-messageformat`, `i18next-resources-to-backend`, plus
`@formatjs/icu-messageformat-parser` (dev — the bundle gate parses with it).
`eslint-plugin-i18next` is a root devDependency.

> The plan also listed `i18next-browser-languagedetector`. It is **not**
> installed: [`detect.ts`](../client/src/i18n/detect.ts) implements the
> resolution order directly, which is a dozen lines, unit-testable, and makes
> the base-tag matching (`fr-CA` → `fr`) explicit rather than configured.

### A vitest gotcha, and why the config carries an inline

`i18next-icu`'s ESM build does `import IntlMessageFormat from
'intl-messageformat'`, and that package ships **no `exports` map**. Node's ESM
resolution therefore picks its CommonJS entry, and the default import lands on
the module object rather than the class — `new IntlMessageFormat(...)` throws,
`parse` swallows it, and every ICU message renders **as its raw source**. It
fails silently, and only under vitest: Vite resolves the ESM entry for the app
build. Hence `server.deps.inline: ['i18next-icu']` in
[vitest.config.ts](../client/vitest.config.ts).

## The module — `client/src/i18n/`

| File | Role |
| --- | --- |
| `index.ts` | The singleton, `initI18n()`, `changeLocale()`, the standalone `t` |
| `detect.ts` | `resolveInitialLocale()` — the resolution order below |
| `document.ts` | `applyDocumentLocale()` — sets `<html lang>` and `<html dir>` |
| `useLocale.ts` | Current locale + `setLocale()` (persists). A `.ts` file, not `.tsx`, so `react-refresh/only-export-components` stays quiet |
| `LocaleSwitcher.tsx` | The interface-language control |
| `NavLocaleSwitcher.tsx` | The same control dressed as nav chrome, for the signed-out pages |
| `format.ts` | `Intl` helpers — relative time, date, number, file size, currency |
| `apiError.ts` | `apiErrorMessage(err, t, fallbackKey)` |
| `locales/{en,fr,es,ru,zh}.json` | One resource bundle per locale, 487 keys each |
| `bundles.test.ts` | The completeness gate |

Keys are dotted and grouped by area: `common.*`, `nav.*`, `auth.*`, `home.*`,
`project.*`, `lecture.*`, `deck.*`, `slide.*`, `image.*`, `whiteboard.*`,
`refine.*`, `transcript.*`, `seed.*`, `access.*`, `quiz.*`, `export.*`,
`profile.*`, `errors.*`.

`en.json` is imported statically; the other four load through
`i18next-resources-to-backend` with a dynamic `import()`, so Vite emits one
chunk per locale (fr 26 kB, es 25 kB, ru 37 kB, zh 22 kB) and a visitor
downloads only theirs. `fallbackLng: 'en'`.

**Adding a sixth locale is a bundle file plus one entry in `LOCALES` and one in
`LOCALE_DIRECTION` — no component changes, and no edit to the loader or the
gate.**

`react: { useSuspense: false }` is set deliberately: switching to a locale whose
chunk is still loading would otherwise suspend, and there is no Suspense
boundary above the shell.

### Locale resolution

1. **Signed in** → `user.locale` wins. An effect inside `AuthProvider` calls
   `changeLocale()` when the user loads or changes.
2. **Anonymous** → `localStorage['sm.locale']`, then `navigator.languages`
   (matched on the base tag, so `fr-CA` → `fr`), then `en`.

Switching writes `localStorage` always, and additionally dispatches
`user.setLocale` when signed in, so the next visit's *pre-auth* paint is already
right. Registration sends the detected locale, so the first-visit detection
persists to the profile rather than being re-guessed.

We do **not** read `Accept-Language` server-side. The SPA is client-rendered, so
there is no server-side render to localize, and `navigator.languages` is the
same browser signal — already used in [capture.ts](../client/src/stt/capture.ts).

### Boot

[`main.tsx`](../client/src/main.tsx) already gated mount on an async config
fetch. The locale bundle joins it, so there is no untranslated first paint:

```ts
void Promise.allSettled([loadRuntimeConfig(), initI18n()]).then(render)
```

## Server changes

Small, and each mirrors code that already existed.

- **`user.setLocale`** in [actions/user.ts](../server/src/actions/user.ts) — a
  direct mirror of the neighbouring `userSetLanguage`, with
  `z.object({ locale: z.enum(LOCALES) })`. Not nullable: unlike `language`,
  `locale` always has a value. Recorded in the settings change log like every
  other account setting.
- **`UserSetLocaleInput`** in [dto/actions.ts](../shared/src/dto/actions.ts).
- **`LOCALE_DIRECTION`** in [types/locale.ts](../shared/src/types/locale.ts) —
  `Record<Locale, 'ltr' | 'rtl'>`, all `ltr` today, so the `dir` attribute has a
  single source of truth when an RTL locale arrives.
- **Registration** ([routes/auth.ts](../server/src/routes/auth.ts)) —
  `registerSchema` gains `locale: z.enum(LOCALES).optional()`; absent leaves the
  schema default.

### Server error messages

The server **stays English**. Localizing it would mean a second bundle
infrastructure on the back end plus localized Zod messages, for strings the
client is better placed to phrase anyway.

Keying client translations off `error.code` alone does not work either:
`not_found` is thrown at 14 sites and `forbidden` at 8, so it would flatten
"Lecture not found", "Slide not found" and "Profile not found" into one message.
So the rule is two-tier, and `err.message` stops reaching the screen:

1. **Globally meaningful codes** — `invalid_credentials`, `account_banned`,
   `unauthorized`, `forbidden`, `internal_error`, `unknown_error` — get
   `errors.<code>` keys.
2. **Everything else** uses a **call-site key**. Most call sites effectively had
   one already, as their local fallback copy (`'Could not load this deck'`);
   those became `deck.errors.load` and friends.

`apiErrorMessage(err, t, fallbackKey)` returns the tier-1 message when the code
is globally meaningful and the call-site message otherwise. The English wording
is unchanged, so [`e2e/tests/auth.spec.ts`](../e2e/tests/auth.spec.ts) — which
asserts "Incorrect email or password", a tier-1 `invalid_credentials` — keeps
passing.

**One deliberate exception.** The admin save path in
[`ProfileSettingsModal`](../client/src/components/ProfileSettingsModal.tsx) still
renders `err.message`: the admin endpoint's refusals name the specific rule that
was hit ("Admin accounts cannot be moderated"), which is worth more to an admin
than a translated generic — and admin surfaces are English by design.

## The switcher, and not confusing it with the other one

Two language controls in one place is the main UX risk here. Both live in the
account settings modal reached from the profile page
([`ProfileSettingsModal`](../client/src/components/ProfileSettingsModal.tsx)),
under headings that say which is which:

- **Interface language** — *"Menus, buttons and messages appear in this
  language."* The owner gets `LocaleSwitcher`, which re-renders the app they are
  looking at. An admin editing someone else's account gets a plain select
  instead: the account being changed is not the one on screen.
- **Lecture language** — *"Speech recognition and generated slides use this
  language."* [`LanguageSelect`](../client/src/components/LanguageSelect.tsx),
  unchanged, with its inherit-cascade semantics.

### Where the interface switcher appears

Signed in, the account settings modal is the only place — one control, where
account settings live.

Signed out there is no profile to reach, so the three pages a visitor can land
on without an account — landing, `/login`, `/register` — mount
[`NavLocaleSwitcher`](../client/src/i18n/NavLocaleSwitcher.tsx) in the public
nav's top-right action area. It portals itself in through
[`ShellActions`](../client/src/components/layout/ShellActions.tsx), so it is a
per-page opt-in rather than shell chrome: `/d/:slug` and `/u/:userId` share the
`PublicShell` and deliberately do **not** get one.

It reads as nav chrome rather than a form field — globe, current language,
chevron, transparent until hovered.

**It is not a `<select>.`** A native select's open list is drawn by the OS, is
unstyleable, and looks nothing like the app around it, so this one is a menu of
our own built to match the hamburger's dropdown — same `rounded-lg
border-slate-200 shadow-lg` card, same outside-click and Escape dismissal. Rows
are `menuitemradio`, the current one indigo with a check. `LocaleSwitcher`'s
select stays in the settings modal, where a form field is what belongs.

Trigger and rows alike use `localeShortLabel`, so every language is named in
itself and nothing else — "Français", not "Français (French)". Someone hunting
for their own language scans for the word they already recognise; the English
gloss `LOCALE_LABELS` carries costs width without offering a second way in. The
gloss stays on the account settings select, which is a labelled form field
rather than nav chrome.

One consequence worth knowing when writing tests or e2e selectors: the trigger's
accessible name is `"<Interface language>: <choice>"` and **both halves are
translated**, so it stops matching `/Interface language/` the moment the user
switches away from English. Re-query by `button[aria-haspopup="menu"]`, not by
name, after a switch.

> An earlier revision put the switcher in
> [`ShellMenu`](../client/src/components/layout/ShellMenu.tsx), the hamburger,
> which reached every route including signed-in ones. It was removed as nav
> clutter and duplication of the settings modal.

## Formatting

[`useTimeAgo`](../client/src/hooks/useTimeAgo.ts) hand-rolled English
pluralization (`+ 's'`) and a hardcoded `'just now'`. That is unfixable by
translation — Russian has four plural categories and Mandarin has one — so it is
rewritten over `Intl.RelativeTimeFormat` in `format.ts`, keeping the 30-second
tick and the signature. Two visible consequences:

- `numeric: 'auto'` yields "yesterday" and "last week" rather than "1 day ago";
  a fresh timestamp reads "now", not "just now".
- The hook holds the clock in state rather than reading `Date.now()` during
  render, which `react-hooks/purity` (rightly) rejects.

`format.ts` also exposes date, number and file-size formatters, plus a currency
formatter — unused today, but [BILL-*](SPEC.md#5-plans-billing--usage-limits)
lands in the same phase and should not re-invent it.

[`lib/date.ts`](../client/src/lib/date.ts) is admin-only, so instead of making it
locale-aware it is **pinned to `en-US`**. That makes the admin tests'
"locale-independent" comments true by construction rather than by luck of the
runner's system locale.

## ICU, and where `<Trans>` earns its keep

Plain `t()` covers almost everything. ICU plurals carry the counts —
`deck.meta`, `home.showAll`, and the three refine-summary clauses — and ICU
`select` carries the two-way phrasings (`common.adminEditNotice`,
`profile.publicProfileHint`, `profile.lectureLanguageDefault`).

`<Trans>` is used in exactly five places, all of them a sentence with an element
*inside* it, where splitting into fragments would deny the translator control of
word order:

| Key | The element |
| --- | --- |
| `deck.settings.scope` | a link to the project-wide settings |
| `refine.slide.intro` | a link to the lecture-wide refine options |
| `layout.fromTemplate` | the template's name, emphasised |
| `deck.empty.howToStart` | the plus and microphone icons |
| `project.new.description` | a greyed-out "(optional)" |

## RTL readiness

All five launch locales are LTR. SPEC asks only that we not preclude adding an
RTL one, so:

- `LOCALE_DIRECTION` + `applyDocumentLocale()` set `<html dir>` per locale. The
  static `lang="en"` in [index.html](../client/index.html) stays as the pre-JS
  default and the boot overrides it.
- Directional Tailwind utilities became logical ones — `ml-`→`ms-`, `mr-`→`me-`,
  `pl-`→`ps-`, `pr-`→`pe-`, `left-`/`right-`→`start-`/`end-`,
  `text-left`/`text-right`→`text-start`/`text-end` — **only in the non-admin
  files already being edited for string extraction.** A blanket sweep would have
  tripled the diff for no present benefit.

Deliberately excluded, and listed here so a future RTL locale has a known punch
list: the admin console, and [`components/slide/`](../client/src/components/slide/)
— slide geometry is authored content, and the whiteboard canvas and GSAP Flip
transitions use physical coordinates on purpose.

## Strings that live outside the client

| Source | What we did |
| --- | --- |
| `LOCALE_LABELS` ([locale.ts](../shared/src/types/locale.ts)) | **Left alone.** Native language names are correct in every locale — that is what a reader scans for. |
| `tts-voices.ts` | Split `label: 'Emma — warm female'` into `name: 'Emma'` plus `voice.descriptions.<id>`. A proper name reads the same everywhere; "warm female" does not. |
| `SLOT_DESCRIPTORS` ([template.ts](../shared/src/types/template.ts)) | Labels moved to `slot.<name>`. See the wrinkle below. |
| `PLAN_TIERS` ([plans.ts](../shared/src/types/plans.ts)) | `plan.tier.*`, instead of rendering the raw enum value. |
| `Layout.label` / `SlotSpec.label` | **Left as data.** They come from authored JSON in `server/config/templates/` ([TEMPLATES.md](TEMPLATES.md)); the honest fix is per-locale labels in the template format, which belongs with [TMPL-4](SPEC.md#tmpl-4-custom-templates-create--edit--save). |
| `Template.name` | `template.names.<id>` for the three the app ships, via [`templateName`](../client/src/i18n/templateName.ts). See the note below. |

**Template names, and why they are not "left as data" too.** They arrive from
the same authored JSON as the layout labels above, but a template's *name* is
what the picker shows, and "Classic / Midnight / Seminar" are the product's own
words — the starter set is chrome that happens to be stored as config.
[`templateName`](../client/src/i18n/templateName.ts) looks the name up as
`template.names.<id>` with the server's name as the i18next `defaultValue`, so
the three built-ins translate and everything else — a user's own template
([TMPL-4](SPEC.md#tmpl-4-custom-templates-create--edit--save)), or one imported
from YAML — keeps the name its author gave it. That is the same
bundle-wins-for-ours, author-wins-for-theirs split as the slot-label wrinkle,
keyed on the id instead of on a comparison. Layout labels stay data because
there are dozens of them per template and they belong in a per-locale template
format, not in the app bundle.

**The slot-label wrinkle.** The server normalizes a bare-name conventional slot
into a `SlotSpec` carrying the English default from `SLOT_DESCRIPTORS`, so by
the time the client sees it, "an author wrote this label" and "the server filled
the default in" look identical. [`slots.tsx`](../client/src/components/slide/slots.tsx)
tells them apart by comparing against the default: a spec label that **is** the
default was filled in for the author, not chosen by them, so the bundle wins.

## Testing

- **`bundles.test.ts` is the CI gate.** For every locale in `LOCALES` it asserts
  a bundle exists, its key set is identical to `en` (nothing missing, nothing
  orphaned), every message parses as ICU, placeholder names match `en`'s for the
  same key, and no value is blank. Bundles are discovered from disk, so adding a
  locale needs no edit here. It runs under `npm test`, which
  [CI](../.github/workflows/ci.yml) already runs — no new workflow step, and it
  fails locally before it fails in CI.
- Unit tests for `detect` (resolution order, `fr-CA`→`fr`, unsupported→`en`,
  blocked storage), `document`, `format` (including Russian's one/few/many),
  `LocaleSwitcher`, and `apiError` (tier-1 hit, call-site fallback).
- Server integration coverage in
  [`locale.test.ts`](../server/test/integration/locale.test.ts): register with
  and without a locale, `user.setLocale` validation, the settings-log entry, and
  that `locale` and `language` do not disturb each other.
- **e2e** — [playwright.config.ts](../e2e/playwright.config.ts) pins
  `use: { locale: 'en-US' }` so the English-selector specs stay deterministic
  regardless of the runner's system locale.
  [`i18n.spec.ts`](../e2e/tests/i18n.spec.ts) opts out with
  `test.use({ locale: 'fr-FR' })`: French chrome on first load → register →
  switch to English on the profile → reload → still English, because it
  persisted to `User.locale`.

The existing client tests pass **unchanged** except for three deliberate wording
changes: `useTimeAgo`'s "just now" → "now", the admin account modal's "Interface
locale" → "Interface language", and `ProfilePage`'s failed-save alert, which now
shows the call-site message rather than the server's.

### Sourcing the four translations

`fr`, `es`, `ru` and `zh` are machine-translated from `en.json` and committed
with `"reviewed": false` in each bundle's `_meta` header, pending a native check.
A missing key falls back to English rather than rendering the key itself.
`GOOGLE_CLOUD_TRANSLATION_KEY` is provisioned in
[env.ts](../server/src/config/env.ts) but unused — the bundles were produced
offline, not through it.

## Enforcing "no hardcoded strings"

`eslint-plugin-i18next`'s `no-literal-string`, at **error**, scoped to
`client/src/**/*.tsx` and ignoring `pages/Admin*.tsx`, `components/admin/**`,
`auth/RequireAdmin.tsx` and `*.test.tsx`. Two options are load-bearing:

- `mode: 'jsx-only'` rather than the default `jsx-text-only`, which never looks
  at attributes — and a good share of this app's copy is in `aria-label`,
  `alt`, `title` and `placeholder`.
- `'jsx-attributes': { include: [...those four...], exclude: [] }`. The empty
  exclude list is what limits checking to that list; without it every other
  attribute (`to`, `href`, `role`, `viewBox`…) would be checked too.

`slot` joins the callee exclusions: `slot('title')` names a layout slot, not
copy.
